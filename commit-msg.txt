semantic tokens: `semanticTokenScopes`, and a refinement seam for VS Code

The observation this acts on: semantic tokens do not *add* colour, they **override** it, so a range whose meaning
the TextMate grammar already knows better comes out worse than if the server had said nothing. Which ranges those
are is a property of *this* editor, its grammar and its theme — so the server cannot decide it and this extension
must.

# `semanticTokenScopes` — the fix that needs no code

`package.json` now maps every type the server sends onto the scope VS Code's own C++ grammar uses for it. This is
VS Code's own mechanism for exactly this: it changes how a type is *drawn* without changing which type it is, so
the server's legend stays the server's and no type number is invented.

The entry that matters is

    "decorator": ["keyword.other.documentation.cpp", "comment.block.documentation.cpp"]

which is how a Doxygen command gets a colour of its own. The server added that type in the commit beside this one;
without this entry it would be drawn as a generic `decorator`, which is a colour, but not the one a reader of
documentation is looking for.

The mapping follows `ms-vscode.cpptools`' naming (`entity.name.function.member.cpp` and friends) rather than
inventing scopes, because a theme author styles by those names. Two scopes are offered per type where a fallback is
useful — a theme that knows `keyword.control.cpp` gets it, one that knows only `keyword.cpp` still gets a colour.

# `src/semanticTokens.ts` — the seam for what a scope cannot fix

A pure module — no `vscode` import, so it is tested in a plain Node.js process like the rest of this extension's
logic — with the decode/encode halves of the protocol's delta walk and a `refineSemanticTokens` entry point.

**The remap table is empty, and that is the honest state rather than an oversight.** Every correction this
extension currently needs turned out to be a *scope* correction, which belongs in `package.json` where a theme
author can see it. The table is kept because the next correction may not be one — anything needing the document's
text or its language has to be applied in code — and because an entry is a judgement about an editor, which is
easier to revisit written down with its reason beside it.

Two rules the module enforces so a refinement cannot break the answer:

* **a remap may only name a type already in the legend.** A target that is absent is *refused* and the server's own
  type is kept: sending a number the client cannot map is worse than sending the colour the server chose.
* **the encoder re-establishes order and non-overlap**, one token per start offset, first claim wins — the same rule
  the server's builder uses, re-applied because a refinement is free to produce tokens the server did not.

# The client's copy of the legend, and what a drift costs

`SERVER_LEGEND` names the server's types in order, because a middleware cannot read the `initialize` result early
enough and a refinement that waited for one would never run. The list is written in two repositories, so
`verifyLegend` exists and `extension.ts` calls it once per connection: a drift costs an **unrefined** colour and
never a wrong one — a name that does not match simply means the remap does not apply — and this turns that silent
cost into a line in the `cppls` log.

# Tests

Six unit tests, and the two that matter are the invariants: the delta walk survives a round trip, and a refinement
cannot reorder or overlap the answer (checked on a file with tokens handed in out of order and two sharing a start
offset — what a rule that inserts something produces). One test reads `package.json` and asserts every scope name it
styles is a type the server can actually send, so an entry for a token that never arrives fails here.

npm run check-types: clean. npm run lint: clean. npm run test:unit: 32 passed (26 before). Bundle verified.
